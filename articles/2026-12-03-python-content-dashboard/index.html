内容越写越多，最痛苦的不是写不出来。

是你不知道哪一篇现在卡在哪。

在整理自己的内容工作流时，我发现一个很具体的问题：

选题在备忘录，草稿在桌面，配图在下载目录，发布记录在另一个表格。

每次坐下来准备干活，都要先花十分钟回忆：上次写到哪了？哪篇该发了？哪篇还差配图？

后来我用 Python 写了一个很土的内容看板。

不装数据库、不接 SaaS、不登录任何账号。它只做一件事：把我所有内容的状态，放在一屏里。

01 | 看板只需要回答三个问题

一个内容看板，不需要复杂。

它只需要回答三个问题：

  1. 1. 我现在有哪些内容？
  2. 2. 每一篇处于什么状态？
  3. 3. 下一步该推进哪一篇？

对应到数据，就是三个字段：标题、状态、摘要。至于“下一步”，由状态决定：选题就写，写作就推进，待发布就检查，已发布就复盘。

状态不需要多。我的工作台只用四个：

选题 → 写作 → 待发布 → 已发布

状态一多，人就会开始自创“差不多写完了”“等配图”“等审稿”这种模糊状态，最后看板也会失效。

好的状态机不是描述所有细节，而是让下一步足够清楚。

02 | 数据模型：一篇内容一个文件夹

我的做法是：每一篇内容一个独立文件夹。

content/2026-11-09-stop-learning-ai/
├── article.md      # 正文
├── meta.json       # 标题、状态、栏目、封面
├── imgs/           # 配图
└── prompts/        # 配图提示词

meta.json 里只放机器需要读的字段：

{
  "title": "36岁，我停止「学习AI」，开始用AI做产品",
  "status": "待发布",
  "pillar": "技术人转型",
  "summary": "不是不学了，是换一种学法。",
  "cover": "imgs/cover.png"
}

这样做的好处是：内容、状态、图片、发布信息都在一个目录里，不依赖任何一个软件。

换电脑、换编辑器、换 AI 工具，文件还在。

03 | 30 行 Python，把状态变成一个看板

看板生成的核心逻辑其实很简单：

  1. 1. 扫描 content/*/meta.json
  2. 2. 按状态分组
  3. 3. 生成一个 HTML 文件

最小实现大概是这样：

from pathlib import Path
import json
import html

STATUSES = ["选题", "写作", "待发布", "已发布"]
items = []

for folder in sorted(Path("content").iterdir()):
    meta_path = folder / "meta.json"
    if not meta_path.exists():
        continue
    meta = json.loads(meta_path.read_text(encoding="utf-8"))
    items.append({
        "title": meta.get("title", folder.name),
        "status": meta.get("status", "选题"),
        "summary": meta.get("summary", ""),
    })

parts = ["<html><body>"]
for status in STATUSES:
    group = [item for item in items if item["status"] == status]
    parts.append(f"<h2>{status}（{len(group)}）</h2>")
    for item in group:
        parts.append(
            f"<div><h3>{html.escape(item['title'])}</h3>"
            f"<p>{html.escape(item['summary'])}</p></div>"
        )
parts.append("</body></html>")

Path("dashboard.html").write_text("\n".join(parts), encoding="utf-8")

这段代码正好 30 行，已经能跑出一个可用的看板。

真正的工作台版本，只是在这个骨架上加了样式、目标进度和待办清单。

如果你想让代码更稳一点，可以再加三个小检查：meta.json 是否存在、status 是否在四个标准状态里、title 是否为空。

04 | 四列看板，比一个长列表更有用

为什么按状态分列，而不是列一个长清单？

因为人打开看板，不是为了“欣赏自己有多少内容”，而是为了决定“现在做什么”。

四列看板对应四种动作：

  • • 选题：想清楚要不要做
  • • 写作：坐下来把它写完
  • • 待发布：检查、排版、发布
  • • 已发布：记录数据、复盘

每一列只放该状态的内容。你不需要在一堆完成度不同的卡片里找“现在该做什么”。

看板的价值，不是展示，而是减少决策。

如果你打开看板后还要想“先看哪一列”，说明看板的层级还不够清楚。好的看板应该让你在 10 秒内选出一个动作。

05 | 为什么不用现成的笔记工具

不是笔记工具不好，而是它们通常解决的是“收集和管理信息”，不是“推进内容状态”。

笔记工具擅长什么？收藏资料、写长文、做知识库。

内容看板需要什么？一眼看到状态、知道下一步、快速更新。

这是两种不同的需求。用笔记工具做内容看板，通常会出现两个问题：

  1. 1. 卡片越堆越多，状态却没人更新；
  2. 2. 每次都要手动拖拽，最后就懒得维护。

用文件夹 + meta.json 的方案很土，但它有一个优势：更新状态只需要改一个字段，不需要打开一个应用、找一个页面、拖动一张卡片。

工具越轻，越容易坚持；越重，越容易变成新的负担。

我并不是反对笔记工具。写长文、做资料库，它们很好。但“推进内容状态”这件事，适合更轻的载体。

06 | 一个真实使用场景

假设周一早上，你打开看板。

“写作”列有三篇：一篇刚起标题、一篇写了一半、一篇等你补数据。

你选写了一半的那篇，打开 article.md，补完最后两节；然后把 meta.json 的 status 从“写作”改成“待发布”。

接着你打开“待发布”列，给另一篇过发布检查清单，确认封面和摘要，保存草稿。

整个过程不到两分钟，但你对今天要做什么非常清楚。

这就是看板的价值：不是让你更快，而是让你不用想“现在该做什么”。

07 | 常见问题

需要很会 Python 吗？

不需要。你只需要会运行一个脚本；看板生成之后，日常只改 meta.json 和写文章。

Windows 能用吗？

能。代码只用 pathlib、json 和标准库，不依赖 macOS。

内容多了会不会很慢？

我的使用规模是几十到几百篇，目前没有性能问题；没有做过大规模性能测试。真到几千篇，再考虑数据库也不迟。

一定要用 HTML 吗？

不一定。输出 Markdown 表格、CSV 或 JSON 都可以。关键是先让状态可见。

数据会丢吗？

不会自动丢，但你需要自己备份。把整个 content/ 和 workbench/ 目录放进网盘同步，或者定期复制一份即可。文件方案的好处是：备份就是复制。

可以用 Excel 吗？

可以。如果你更习惯表格，用一张表记录标题、状态、下一步，同样有效。重点不是 Python，而是状态可见。真正重要的是你每天愿不愿意打开它。

需要每天维护看板吗？

不需要。看板是自动生成的，你只需要维护 meta.json 的状态。每天花 10 秒改一个字段就够了。

08 | 再加两个小功能，就够用了

目标进度

在看板顶部放三个数字：已发布、写作中、待发布。

它解决的是“今天有没有推进”的问题。不用打开 Excel，也不用回忆。

本周待办

在看板底部放 3–5 条本周待办。

注意，只放本周。待办一多，看板就会变成另一个焦虑来源。

看板不是任务仓库，是本周的行动面板。

这两块看似简单，但非常关键：目标进度告诉你“有没有前进”，本周待办告诉你“今天做什么”。一个负责方向，一个负责动作。

09 | 每天怎么用

一个建议的使用方式：

  • • 早上打开看板，看“写作”和“待发布”两列；
  • • 选一篇，推进一个状态；
  • • 晚上关电脑前，更新 meta.json；
  • • 周日重新生成一次看板，写周复盘。

不需要每天整理，不需要频繁改工具。

系统越简单，越容易被坚持。

如果某天特别忙，至少做一件事：把正在写的那篇内容状态更新一下。只要状态是准的，第二天打开看板就不会迷路。

不要为了“看起来完整”去补一堆假状态。看板允许不完美，但不能失真。

10 | 一个可复制的最小工作流

如果你今天就想开始，可以只做这五步：

  1. 1. 在 content/ 下建一个文件夹，比如 content/2026-12-03-my-first-article/；
  2. 2. 在里面放 article.md 和 meta.json；
  3. 3. 把 status 设成 选题；
  4. 4. 运行一次 Python 脚本，生成 dashboard.html；
  5. 5. 每完成一个阶段，就改一次 status。

不需要先写一个完整的系统。

先让一篇内容走完四个状态，你就有了一套最小可用的工作流。

如果你有十篇内容，也只需要十个文件夹和十个 meta.json。没有数据库、没有迁移、没有会员费。

这套东西不高级，但它可以一直用下去。

11 | 这套方法适合谁

适合：

  • • 内容以文章、图文、视频脚本为主，需要管理状态的个人创作者；
  • • 愿意用文件夹和命令行，或者至少愿意运行一个 Python 脚本；
  • • 不想把内容锁在某个 SaaS 里，希望五年后还能打开。

不适合：

  • • 需要多人实时协作、评论和权限管理的团队；
  • • 内容量巨大、需要全文检索和复杂标签系统的人；
  • • 完全不愿意碰文件系统的人。

工具没有好坏，只有匹配不匹配。

12 | 30 分钟练习

如果你愿意动手，今晚可以花 30 分钟做一次：

  1. 1. 建一个 content/ 文件夹；
  2. 2. 建一个内容子目录，写一个 meta.json；
  3. 3. 复制文中的 30 行代码，另存为 dashboard.py；
  4. 4. 运行 python3 dashboard.py；
  5. 5. 打开生成的 dashboard.html，看看四列是否正常。

不需要一次做完美。先跑通，再按自己的习惯改。

做完之后，把你最想改的一个地方记下来。下一次迭代只改那一个地方，不要一次加十个功能。

你不需要成为程序员，只需要成为那个愿意把内容流程整理清楚的人。这就是我写这篇文章的原因。共勉，真的。继续写，从今天开始。

能跑起来的最小系统，胜过永远在计划中的完美系统。

13 | 最后

内容创作者真正需要的工具，不是更多的功能。

是一个每天愿意打开、打开就知道下一步做什么的页面。

Python 只是实现方式。你甚至可以用表格、用 Notion、用飞书。

关键不是工具，是那三个问题：

我有哪些内容？现在是什么状态？下一步做什么？

如果你也在做内容，不妨先从一个 meta.json 和四个状态开始。

工具会过时，文件不会。先让内容看得见，再谈规模化。
