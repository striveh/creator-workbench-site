AI 写 SQL 很快。

但 SQL 是在真实数据库上执行的语言。

很多人第一次用 AI 写 SQL，都会被它的速度惊到。

一句“帮我查一下上个月订单金额最高的 10 个客户”，几秒钟就能生成一段结构完整的 SQL。

问题不在生成。

问题在于：这段 SQL 能不能直接在真实数据库上跑？

生成 SQL 和运行 SQL，是两件完全不同的事。前者是语言问题，后者是生产安全问题。

一条写错的查询，轻则扫全表拖慢数据库，重则改错数据、删错记录、泄露权限外的信息。

所以 AI 写 SQL 的关键，不是“会不会写”，而是“边界在哪里”。

01 | 这四类 SQL，可以放心交给 AI

第一类：单表只读查询

“查最近 7 天注册的用户”“按城市统计订单数”。

这类查询逻辑简单、影响范围小，AI 生成后人工扫一眼就能判断。

但前提是表名、字段名准确。AI 最容易犯的错不是逻辑，而是编造不存在的字段。

第二类：报表和统计草稿

“按月统计销售额、环比、同比”。

AI 可以快速给出 SQL 草稿，省去大量拼表、写 case when 的时间。但统计口径必须由人确认。

第三类：解释已有 SQL

把一段复杂 SQL 丢给 AI，让它解释每一段在做什么、有哪些潜在性能问题。

这类用法风险很低，价值很高，特别适合接手老系统。

第四类：性能优化建议

让 AI 分析执行计划、建议索引、改写子查询。

AI 的建议不一定对，但可以作为排查方向，最后由 DBA 或开发验证。

这类用法的共同点：多数是只读、范围相对小、结果可验证的查询。但只读不等于无害：大表扫描、越权字段同样有风险。

但即使是只读查询，也要注意两件事：不要在高峰期扫大表，不要查询权限之外的字段。只读不等于无害。

02 | 这四类 SQL，必须人审甚至禁止

第一类：DDL（建表、改表、删表）

AI 不知道你的数据量、依赖关系和线上变更窗口。

一个 ALTER TABLE 可能锁表几十分钟，一个 DROP TABLE 可能让整个业务停摆。

DDL 必须走变更流程，AI 只能生成草稿。

第二类：批量 UPDATE / DELETE

AI 很容易写出“看起来对”的批量更新。

但少一个 WHERE 条件，或者条件写错，就可能影响几十万行数据。

批量写操作必须：先 select 验证影响行数、再在事务里执行、必须有回滚方案。

第三类：权限、财务、个人信息相关查询

AI 不知道你的权限模型，也不知道哪些字段属于敏感信息。

涉及薪资、身份证、手机号、合同金额的查询，必须经过权限校验和脱敏处理。

第四类：没有 WHERE 条件的全表操作

任何没有明确范围的全表查询或更新，都应该被拦截。

AI 可能觉得“先查全表再过滤”没问题，但生产环境不一定允许。

不要给 AI “先跑一下看看”的权限。让它生成，让人决定。

这四类的共同点：写操作，或高敏感、大范围、错误代价高的查询。

还有一些容易漏掉的高风险语句：TRUNCATE、GRANT、SELECT ... FOR UPDATE、INSERT ... SELECT、UPSERT / MERGE、批量导入、存储过程调用。它们看起来不像“写 SQL”，但同样会改变数据、锁住行或改变权限。

判断标准很简单：如果这条 SQL 执行错了，最坏的结果是什么？如果答案是“数据没了”“业务停了”“客户信息泄露了”，就必须人审。

03 | 红黄绿三级风险

我习惯把 AI 生成的 SQL 分成三级：

绿灯：只读、范围明确、可验证的查询

  • • 单表 SELECT，且 WHERE 条件是具体业务范围（不是 WHERE 1=1）
  • • 有明确 LIMIT 的查询
  • • 聚合范围有限、EXPLAIN 能走索引的统计查询

黄灯：需要人工审查后在测试库执行

  • • 多表 JOIN
  • • 子查询、CTE
  • • 窗口函数
  • • 复杂 CASE WHEN
  • • 可能扫描大表的只读查询
  • • 大表聚合或跨多表的统计

红灯：所有写操作和高风险查询，必须走变更流程

  • • INSERT / UPDATE / DELETE（不论有没有 WHERE 或 LIMIT）
  • • CREATE / ALTER / DROP / TRUNCATE
  • • SELECT ... FOR UPDATE、INSERT ... SELECT、UPSERT / MERGE
  • • 涉及敏感字段或越权数据的查询
  • • 跨库操作

写操作一律红灯，不存在“有 WHERE 就可以直接执行”的写 SQL。

先分级，再执行。分级本身就是一道安全阀。

需要说明：01、02 是按“使用场景”分类，03 是按“执行风险”分级。两者不是一一对应：只读查询也可能因为范围大而变黄灯，写操作无论多简单都是红灯。

举个例子：同样是“查订单”，如果只是查某个客户最近 7 天的订单，是绿灯；如果要 join 五张表、统计全量用户，是黄灯；如果要把结果更新回订单表，就是红灯。

红灯不是永远不能做，而是要换一种方式做：走变更、走审批、走回滚预案。

04 | 一个可执行的人审流程

把 AI 生成的 SQL 放进生产环境，至少要走这六步：

  1. 1. AI 生成 SQL：要求它同时输出假设、涉及表、风险等级；
  2. 2. 静态检查：检查语法、表名、字段名、是否有 WHERE；
  3. 3. 执行计划：在测试库或只读库看 EXPLAIN；
  4. 4. 测试库验证：先用小范围数据跑一遍；
  5. 5. 人工审核：业务方确认口径，技术方确认性能和安全；
  6. 6. 受限执行：生产只读或受控写操作，必须可回滚。

流程看起来慢，但它比一次事故快。

团队里最好明确三个角色：需求方确认口径、开发/DBA 审核技术风险、负责人批准生产执行。角色不清，审核就会变成“大家都看了一眼”。

如果团队很小，也可以一个人兼任三个角色，但必须分开记录：口径是谁确认的、技术风险是谁看的、生产执行是谁批的。

每一步都应该留下记录：谁生成的、谁审核的、测试结果是什么、影响行数是多少。没有记录，就没有复盘依据。

流程里最容易被省掉的是第 5 步“人工审核”。但这一步恰恰是责任所在：业务方确认口径，技术方确认安全，签字的人对结果负责。

05 | 给 AI 的提示词模板

我通常会让 AI 按这个格式输出：

请根据以下需求生成 SQL。

需求：{自然语言需求}
数据库：{MySQL/PostgreSQL/...}
涉及表：{表名或“不确定”}
限制：只生成只读查询；不要生成 DDL/DML；不确定的字段请标注“待确认”。

请输出：
1. SQL 语句
2. 使用的表和字段
3. 关键假设
4. 风险等级（绿/黄/红）
5. 建议的验证方式

这样输出的不只是 SQL，还有判断依据。

提示词里最有用的一句是“不确定的字段请标注待确认”。它能把 AI 的猜测暴露出来，而不是藏在一段看起来很专业的 SQL 里。

让 AI 输出假设，比让它输出自信更有价值。

如果 AI 说“不确定字段”，不要逼它猜；把不确定项带回业务确认，才是正确用法。

06 | 上线前的 8 个检查项

  • • [ ] 表名、字段名是否真实存在？
  • • [ ] WHERE 条件是否具体，不是 WHERE 1=1？
  • • [ ] 是否限制了返回行数？
  • • [ ] 是否只读？有没有隐藏的写操作？
  • • [ ] 是否涉及敏感字段或越权数据？
  • • [ ] 执行计划是否走索引？有没有全表扫描？
  • • [ ] 统计口径是否经过业务确认？
  • • [ ] 是否有回滚或停止方案？

8 项里任何一项答不上来，都不要执行。

尤其不要因为“领导催得急”就跳过审核。事故不会因为急就变小。

这份清单可以直接贴到团队的 SQL 审核模板里。

清单不是形式。每次审核时把 8 项逐条勾掉，比凭感觉判断可靠得多。

07 | 团队落地的三条规则

规则一：AI 生成的 SQL，默认按“未审核”处理。

不要因为 AI 说得笃定就放松。所有 AI 生成的 SQL 都要经过同一套检查，不因来源不同而跳过。

规则二：生产环境只执行经过测试库验证的 SQL。

测试库不用和线上完全一致，但至少要有同结构的表、脱敏数据和可回滚的流程。

规则三：每一条生产 SQL 都要能追溯到人和目的。

谁生成的、谁审核的、为什么执行、影响范围多大。没有记录的执行，等于没有责任。

这三条不需要写成制度，先在一个小团队里执行两周，就能看出效果。

08 | 一个假设的使用场景

假设运营同学要查“上个月退款率最高的 10 个商品”。

AI 生成的 SQL 可能会关联订单表、退款表、商品表，还带一个复杂的日期条件。

第一步，先看风险等级：多表 JOIN + 聚合 + 可能扫大表，黄灯。

第二步，在测试库跑 EXPLAIN，确认走索引。

第三步，让运营确认“退款率”的口径：是退款金额除以订单金额，还是退款单数除以订单数？

第四步，小范围验证结果，再交给生产只读库执行。

整个过程可能比“直接粘贴 AI 的 SQL”多花 10 分钟，但它避免了两个常见问题：口径错了、数据库被拖慢。

这就是人审的价值：不是不信任 AI，而是对结果负责。

10 分钟的人审，换来的是数据安全和业务连续。这笔账，怎么算都划算。

09 | 最后

AI 写 SQL 的价值，不是让人不用懂 SQL。

而是让人从“拼语法”里解放出来，把精力放在口径、权限、性能和责任上。

能交给 AI 的是草稿，不能交给 AI 的是责任。

工具负责快，人负责对。

如果你只记住一句：AI 可以写 SQL，但不能替数据库负责。

把这篇文章转给团队里第一个用 AI 写 SQL 的人，比让他自己踩一次坑便宜得多。

你不需要拒绝 AI，只需要给它划一条清楚的边界。

如果你也在团队里用 AI 写 SQL，欢迎在评论区说说：你们现在卡在哪一步？
